## 2. Reglas de las órdenes de compra y producción

### 2.1 Órdenes de compra (OC)

De acuerdo con `04_integridad_ordenes.md`, el proceso está diseñado para **sugerir compras cuando el material baja del punto de reorden**. Antes de aprobar o continuar con una OC, se debe revisar que sus datos sean correctos y que exista la autorización correspondiente.

Validaciones necesarias:

1. Identificar proveedor, material y cantidad solicitada.
2. Comprobar que la cantidad sea válida y que la necesidad de compra esté justificada.
3. Revisar las condiciones de aprobación antes de emitir la orden.
4. Evitar registrar la misma operación dos veces.
5. Comprobar la recepción de materiales antes de autorizar un pago, como indica la política descrita en `04_integridad_ordenes.md`.

**Ejemplo de referencia:** el evento `InvoiceApprovedForPaymentEvent` (`EVT-ERP-PAY-001`) relaciona la factura `INV-994812` con la OC `PO-2026-00451`, el recibo `GRN-2026-0982` y aprobaciones de compras y finanzas. Es un ejemplo del **proceso de pago**, no prueba que todas las OC utilicen esos mismos aprobadores.

### 2.2 Órdenes de producción (OP)

El mismo documento señala que las OP se proponen cuando existe demanda de un producto terminado. Para liberarlas, es necesario comprobar los componentes requeridos y las existencias disponibles.

Validaciones necesarias:

1. Identificar el producto y la cantidad a fabricar.
2. Consultar la lista de materiales correspondiente.
3. Calcular las cantidades necesarias, incluyendo la merma cuando aplique.
4. Comparar las necesidades con el material disponible.
5. Detener la liberación si hay faltantes que impidan completar la producción.

Estas son condiciones del proceso documentado; **no se ha comprobado** en el código cómo se autoriza o cambia de estado una OC u OP.

## 3. Validaciones antes de confirmar un pedido

Los diagramas `OrderDeliveryFlow.md` y `DiagramaModelo_175456.md` muestran las decisiones principales del flujo de venta. El PDF asigna códigos a varias de esas reglas:

| Validación | Regla o requisito | Resultado esperado |
|---|---|---|
| Cliente y producto válidos | RF-03 y RN-04 | Cliente activo y producto registrado. |
| Crédito del cliente | RN-04 | Dentro del límite o enviado a la autorización que corresponda. |
| Cantidad, precio y descuento | RN-08 | Cantidad mayor a 0, precio no negativo y descuento entre 0 % y 100 %. |
| Período contable | RN-05 | Debe estar abierto. |
| Existencias | RF-04 y RN-03 | Debe haber unidades suficientes para la salida. |
| Importes del documento | RN-09 | Total calculado correctamente. |
| Registro contable | RF-05 y RN-02 | Cargos y abonos iguales. |

**Orden del proceso descrito en `OrderDeliveryFlow.md`:** iniciar operación → revisar crédito → pedir autorización al supervisor si no alcanza → comprobar período contable → revisar existencias y costos → generar asiento contable → comprobar relaciones de datos → controlar errores, registrar la operación y finalizar. Si hay un error, el diagrama indica rechazo o reversión.

`DiagramaModelo_175456.md` detalla el recorrido entre **Ventas, Inventarios, Cuentas por Cobrar, Contabilidad y Auditoría**: tras confirmar el pedido, se validan las existencias, se registra la factura o cuenta por cobrar, se genera una póliza balanceada y finalmente se confirma la operación. Los diagramas representan el **flujo esperado**, no evidencia de que todos sus pasos estén programados. Además, los dos diagramas presentan distintos niveles de detalle: uno muestra la autorización del supervisor y el otro explica cómo se relacionan los módulos. No deben interpretarse como dos implementaciones verificadas.

## 4. Crédito del cliente y autorización del supervisor

La regla **RN-04** permite ventas a clientes activos que respeten su límite de crédito. La prueba **PU-04** del PDF contempla rechazar o solicitar autorización cuando `saldo + venta > límite`.

**Ejemplo:** si el límite es $20,000, el cliente debe $15,000 y quiere comprar $8,000, el saldo total sería $23,000. Se excede el límite en $3,000. El diagrama `OrderDeliveryFlow.md` manda este caso a **autorización del supervisor**; si la niega, la operación se bloquea. El PDF también admite el rechazo según la política aplicable.

La documentación agrega dos casos de autorización:

- **RN-08:** descuentos superiores al porcentaje configurado requieren aprobación. El PDF usa 15 % solo como ejemplo de umbral.
- **RN-10 y RF-10:** cancelar documentos exige rol autorizado, motivo y, cuando corresponda, una nota de crédito.

La autorización debe quedar registrada. No debe suponerse que cualquier supervisor puede cambiar el límite de crédito sin seguir las políticas del sistema.

## 5. Período contable, existencias y costos

### 5.1 Período contable

**RN-05** indica que no deben registrarse movimientos con fecha en un período cerrado. Por ejemplo, si octubre ya está cerrado, una venta fechada en ese mes se rechaza. El PDF plantea esta validación en **PU-09** y **PF-08**, y `OrderDeliveryFlow.md` también muestra el rechazo si el período está cerrado.

### 5.2 Existencias

**RF-04** exige revisar el inventario antes de descontarlo. **RN-03** impide una salida mayor a lo disponible, salvo que exista una excepción autorizada por la empresa. `DiagramaModelo_175456.md` muestra que, si la existencia no alcanza, se revierte la operación.

**Ejemplo:** hay 3 unidades disponibles y se solicitan 5. El resultado esperado de **PU-06** es rechazar la salida y mantener el inventario sin cambios.

### 5.3 Costos e importes

`OrderDeliveryFlow.md` incluye la pregunta **«¿Existencias y Costos OK?»**. El PDF concreta que los precios no pueden ser negativos (**RN-08**), que los totales deben coincidir (**RN-09**) y que la moneda y el tipo de cambio se fijan al registrar la operación (**RN-12**).

Para las OP, se recomienda verificar el costo de cada material antes de calcular el costo de fabricación. **No se encontró una fórmula ni un método de costeo específico** en los archivos adjuntos, así que no se atribuye al ERP una implementación que no se ha revisado.

## 6. Asientos contables balanceados

**RF-05 y RN-02** establecen que la suma de cargos (Debe) debe ser igual a la de abonos (Haber). El PDF incluye las pruebas **PU-07** y **PU-08** para aceptar una póliza balanceada y rechazar otra con diferencias.

**Ejemplo sencillo de una venta sin impuestos:**

| Cuenta | Debe | Haber |
|---|---:|---:|
| Clientes | $1,000.00 | $0.00 |
| Ventas | $0.00 | $1,000.00 |
| **Total** | **$1,000.00** | **$1,000.00** |

La póliza está balanceada. Si en Ventas se registraran solo $900, el sistema tendría que rechazarla porque existiría una diferencia de $100.

Como otro ejemplo, el evento de pagos **`GeneralLedgerPostedEvent` (`EVT-ERP-PAY-009`)** contiene un cargo de $150,000 a cuentas por pagar y un abono de $150,000 a bancos. **Es información del ejemplo de eventos**, no una prueba de que el asiento se haya registrado en una base de datos real.

## 7. Reglas de las listas de materiales (BOM)

`04_integridad_ordenes.md` señala que una BOM debe mantener las relaciones correctas entre productos y materiales. Documenta estas reglas lógicas:

1. **Sin ciclos:** un producto no puede terminar requiriéndose a sí mismo a través de sus componentes.
2. **Tipo de artículo correcto:** una materia prima no debe aparecer como producto padre de un ensamble.
3. **Versiones activas protegidas:** no se deben editar directamente las versiones de BOM marcadas como activas.
4. **Cantidades válidas:** las cantidades de componentes deben ser mayores a cero.
5. **Merma:** si un proceso pierde material durante la fabricación, ese porcentaje debe considerarse al calcular lo necesario.

El documento de referencia menciona que `sql/init.sql` relaciona `bill_of_materials` con `products` y `materials`. También señala que `src/check_shortages.py` usa `bill_of_materials`, `sales_orders` e `inventory` para calcular faltantes. **Estas descripciones proceden de `04_integridad_ordenes.md`; no se verificaron directamente esos archivos.**

**Ejemplo ilustrativo:** si una BOM requiere cuatro patas por mesa, fabricar 10 mesas exige 40 patas. Si solo hay 30 disponibles, faltan 10. No debería liberarse la orden completa sin resolver ese faltante.

## 8. Operaciones que pueden continuar o deben rechazarse

| Situación | Decisión esperada | Referencia |
|---|---|---|
| Pedido válido, dentro de crédito, con inventario suficiente y período abierto. | Continuar con el registro y las demás comprobaciones. | RF-03, RF-04, RN-04, RN-05. |
| Crédito insuficiente, pero el supervisor autoriza. | Continuar con las demás validaciones. | `OrderDeliveryFlow.md`. |
| Crédito insuficiente y autorización denegada. | Rechazar. | `OrderDeliveryFlow.md`. |
| Cliente inactivo. | Rechazar. | RN-04, PU-03. |
| Se solicitan 5 unidades y hay 3. | Rechazar sin afectar inventario. | RF-04, RN-03, PU-06. |
| Fecha dentro de un período contable cerrado. | Rechazar. | RN-05, PU-09, PF-08. |
| Cargos y abonos de la póliza distintos. | Rechazar la póliza. | RN-02, PU-08. |
| OP con materiales insuficientes. | Detener su liberación hasta corregir el faltante. | Reglas del proceso MRP descritas en `04_integridad_ordenes.md`. |
| BOM con una relación circular o modificación directa de versión activa. | No aceptar ese cambio. | Reglas lógicas descritas en `04_integridad_ordenes.md`. |
| Pago a proveedor sin recepción completa registrada. | No autorizar el pago. | Política descrita en `04_integridad_ordenes.md`. |

## 9. Fragmento de código de ejemplo

Este código es **una propuesta ilustrativa**, no una función extraída del repositorio. Resume algunas de las decisiones previas a una venta:

```python
def revisar_pedido(cliente_activo, saldo, limite, total,
                   cantidad, stock, periodo_abierto, autorizado=False):
    if not cliente_activo:
        return "RECHAZAR: cliente inactivo"
    if cantidad <= 0:
        return "RECHAZAR: cantidad no válida"
    if saldo + total > limite and not autorizado:
        return "SOLICITAR AUTORIZACIÓN: crédito insuficiente"
    if not periodo_abierto:
        return "RECHAZAR: período contable cerrado"
    if cantidad > stock:
        return "RECHAZAR: inventario insuficiente"
    return "CONTINUAR: revisar costos y asiento contable"
```

La función no confirma la venta ni modifica existencias. Solo representa las validaciones descritas; en el ERP real faltarían las comprobaciones de precios, descuentos, relaciones de datos y balance contable, entre otras.

## 10. Riesgos identificados y mejoras propuestas

El archivo `04_integridad_ordenes.md` menciona tres riesgos que pueden afectar las órdenes:

| Riesgo documentado | Consecuencia | Mejora propuesta en la fuente |
|---|---|---|
| `src/mrp.py` calcula con una BOM fija en el código en lugar de consultar la base de datos. | Las cantidades pueden diferir de las registradas en el ERP. | Consultar `bill_of_materials` desde el cálculo MRP. |
| Faltan restricciones numéricas tipo `CHECK` en `sql/init.sql`, según la revisión documentada. | Podrían aceptarse cantidades no válidas. | Comprobar y agregar límites para cantidades positivas y existencias no negativas. |
| `src/check_shortages.py` calcula faltantes sin bloqueos, según la revisión documentada. | Dos órdenes podrían considerar disponible el mismo material. | Proteger la lectura y reserva de inventario cuando haya operaciones simultáneas. |

Estas observaciones **son hallazgos reportados por el documento de referencia**, no una inspección nueva del código. Para confirmarlas se necesitaría abrir las versiones actuales de los tres archivos mencionados.

Además, se propone mostrar mensajes claros de rechazo y registrar quién autorizó las excepciones. El PDF incluye controles de auditoría (RF-07) y de operaciones repetidas (RF-09). El detalle técnico de transacciones y concurrencia corresponde a los integrantes asignados a esos temas.
